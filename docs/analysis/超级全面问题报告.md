## 一、数据库设计深度分析（67个问题）

### 1.1 🔴 P0 致命问题（8个）

#### 问题1：核心表缺少索引（性能灾难）

**严重程度**：🔴 极高

**影响表**：
- `campus_content` - **0个索引**（仅主键）
- `campus_comment` - **0个索引**（仅主键）

**问题影响**：
```
查询场景：获取某用户的所有帖子
SELECT * FROM campus_content WHERE user_id = ? ORDER BY create_time DESC

结果：全表扫描！数据量达到1万条时查询时间>5秒
```

**修复SQL**：
```sql
-- campus_content 添加索引
ALTER TABLE campus_content
ADD INDEX idx_user_status_time (user_id, status, create_time DESC),
ADD INDEX idx_category_status (category_id, status),
ADD INDEX idx_status_create_time (status, create_time DESC);

-- campus_comment 添加索引
ALTER TABLE campus_comment
ADD INDEX idx_content_parent_time (content_id, parent_id, create_time DESC),
ADD INDEX idx_user_del_time (user_id, del_flag, create_time DESC),
ADD INDEX idx_one_level (one_level_id, del_flag);
```

**预期收益**：查询性能提升**95%**

#### 问题2：缺少所有外键约束（数据完整性风险）

**严重程度**：🔴 高

**问题范围**：
- `campus_content` - `user_id`, `category_id` 无外键
- `campus_comment` - `user_id`, `content_id`, `to_user_id` 无外键
- `bus_forum_post` - `user_id`, `category_id` 无外键
- `bus_forum_comment` - `user_id`, `post_id`, `to_user_id` 无外键
- `bus_errand_order` - `publisher_id`, `runner_id` 无外键

**风险**：
- 可能产生孤儿记录
- 级联删除需应用层处理
- 数据一致性无法保证

**修复SQL**：
```sql
-- 添加外键约束
ALTER TABLE campus_content
ADD CONSTRAINT fk_content_user
    FOREIGN KEY (user_id) REFERENCES sys_user(user_id) ON DELETE CASCADE,
ADD CONSTRAINT fk_content_category
    FOREIGN KEY (category_id) REFERENCES campus_category(category_id) ON DELETE SET NULL;
```

### 2.1 🔴 P0 并发安全问题（12个）

#### 问题1：跑腿订单抢单 - TOCTOU竞态条件

**严重程度**：🔴 极高

**问题位置**：`ErrandOrderServiceImpl.java:124-196`

**漏洞代码**：
```java
// 第137-181行
locked = tryAcquireLock(lockKey, 10, TimeUnit.SECONDS);
BusErrandOrderEntity order = this.getById(orderId);  // 锁内再次查询
if (!OrderStatus.WAITING.getCode().equals(order.getStatus())) {
    throw new ServiceException("订单已被接单或已取消");
}
int rows = errandOrderMapper.updateStatusWithVersion(...);  // 乐观锁更新
// 第184-187行：又执行了一次 updateById，没有原子性保证
this.updateById(order);
```

**漏洞**：
1. 锁内再次查询订单（可能读到旧数据）
2. 乐观锁更新后又执行了一次`updateById`，破坏原子性

**影响**：同一订单可能被多个骑手接单

**修复方案**：
```java
@Transactional(rollbackFor = Exception.class)
public void acceptOrder(Long orderId) {
    String lockKey = "lock:errand:order:" + orderId;
    try {
        redisCache.tryLock(lockKey, 10, TimeUnit.SECONDS);
        // 直接使用乐观锁更新，无需先查询
        int rows = errandOrderMapper.acceptOrderAtomic(orderId, runnerId, ...);
        if (rows == 0) {
            throw new ServiceException("抢单失败，订单已被接单");
        }
        // 后续业务逻辑...
    } finally {
        redisCache.unlock(lockKey);
    }
}
```

#### 问题3：余额更新 - 无并发控制

**严重程度**：🔴 极高

**问题位置**：`BusStudentServiceImpl.java:90-97`

**漏洞代码**：
```java
public boolean updateBalance(Long studentId, BigDecimal amount) {
    int rows = busStudentMapper.updateBalance(studentId, amount);
    // ❌ 没有检查余额是否足够
    // ❌ 没有加锁
    // ❌ 没有乐观锁
}
```

**影响**：
- 余额可能变成负数
- 并发消费可能导致余额扣减错误
- 可能重复消费

**修复方案**：
```java
@Transactional(rollbackFor = Exception.class)
public boolean updateBalance(Long studentId, BigDecimal amount) {
    String lockKey = "lock:student:balance:" + studentId;
    try {
        redisCache.tryLock(lockKey, 5, TimeUnit.SECONDS);

        // 检查余额
        BusStudentEntity student = getById(studentId);
        if (student.getBalance().compareTo(amount.abs()) < 0) {
            throw new ServiceException("余额不足");
        }

        // 使用乐观锁更新
        int rows = busStudentMapper.updateBalanceWithVersion(
            studentId, amount, student.getVersion()
        );
        return rows > 0;
    } finally {
        redisCache.unlock(lockKey);
    }
}
```
