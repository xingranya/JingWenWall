```sql
UPDATE bus_errand_order
```

### ⚠️ 真正的问题

#### 问题A: 重复代码(低风险)

第184-186行完全重复了第165-167行的操作,虽然不影响功能,但是代码冗余。

#### 问题B: version字段不匹配风险(中风险)

执行流程:
1. 第144行:查询order,version=5(假设)
2. 第172-177行:`updateStatusWithVersion`更新数据库version=6,但order对象中version还是5
3. 第187行:`updateById`使用order对象,version=5

**updateById生成的SQL**:
```sql

  AND version = 5  -- ⚠️ 但数据库中version已经是6了!
```

**结果**: `updateById`会**失败**(影响行数=0),**但代码没有检查返回值**!

#### 问题C: 数据不一致风险(中高风险)

由于第187行的`updateById`会失败,所以:
- runner_id、runner_fee、platform_fee **没有被更新到数据库**
- 只有status和version被更新了(通过updateStatusWithVersion)
- **数据不一致**!

### ✅ 正确的修复方案

**修改 ForumPostServiceImpl.java:184-214**

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void likePost(Long postId) {
    Long userId = SecurityUtils.getUserId();

    // 1. 忽略逻辑删除，直接查询物理记录（确保能找回已删除的记录，规避唯一索引冲突）
    BusForumPostLikeEntity existLike = likeMapper.selectOnePhysical(userId, postId);

    boolean isNewLike = false;  // ✅ 标记是否是新点赞

    if (existLike != null) {
        // 如果记录存在且 del_flag 为 0 (未删除)，说明是真的重复点赞
        if (existLike.getDelFlag() != null && existLike.getDelFlag() == 0) {
            throw new ServiceException("已经点赞过了");
        } else {
            // 如果记录存在但 del_flag 为 1 (已删除)，则将其恢复
            existLike.setDelFlag(0);
            likeMapper.updateById(existLike);
            // ✅ 恢复点赞,不增加计数
        }
    } else {
        // 2. 如果物理表完全没有记录，则执行插入
        BusForumPostLikeEntity likeEntity = new BusForumPostLikeEntity();
        likeEntity.setUserId(userId);
        likeEntity.setPostId(postId);
        likeEntity.setDelFlag(0);
        likeMapper.insert(likeEntity);
        isNewLike = true;  // ✅ 标记为新点赞
    }

    // 3. ✅ 修复:只有新点赞才增加计数,并使用原子性更新
    if (isNewLike) {
        forumPostMapper.incrementLikeCount(postId);
    }
}
```

## 🔴 问题4: SimpleDateFormat线程安全 - 验证分析

### 实际代码

**文件**: `ErrandOrderServiceImpl.java:336-341`

```java
private String generateOrderNo() {
    SimpleDateFormat sdf = new SimpleDateFormat("yyyyMMddHHmmss");
    String timestamp = sdf.format(new Date());
    String random = IdUtil.fastSimpleUUID().substring(0, 6).toUpperCase();
    return "ER" + timestamp + random;
}
```

### ✅ 问题确认

**SimpleDateFormat确实线程不安全**,但由于这里是**局部变量**(每次创建新实例),所以**不存在线程安全问题**。

但是,**每次创建新实例效率低**,建议改为:

```java
private static final DateTimeFormatter FORMATTER =
    DateTimeFormatter.ofPattern("yyyyMMddHHmmss");

private String generateOrderNo() {
    String timestamp = LocalDateTime.now().format(FORMATTER);
    String random = IdUtil.fastSimpleUUID().substring(0, 6).toUpperCase();
    return "ER" + timestamp + random;
}
```

**这不是线程安全问题,而是性能优化问题**。

## ✅ 问题6: ThreadLocal内存泄漏 - 验证分析

### 实际代码

**文件**: `AuthenticationContextHolder.java:11`

```java
private static final ThreadLocal<Authentication> contextHolder = new ThreadLocal<>();
```

### ⚠️ 问题确认

**ThreadLocal在线程池环境下确实会内存泄漏**,因为:
1. 线程池中的线程是复用的
2. ThreadLocal的生命周期与线程绑定
3. 如果不手动清理,会一直占用内存

### ✅ 正确的修复方案

**新建过滤器**:

```java
package com.oddfar.campus.framework.filter;

import com.oddfar.campus.framework.security.context.AuthenticationContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import javax.servlet.FilterChain;
import javax.servlet.ServletException;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;

@Component
public class AuthenticationCleanupFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {
        try {
            filterChain.doFilter(request, response);
        } finally {
            AuthenticationContextHolder.clearContext();
        }
    }
}
```
